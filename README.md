# SQL-анализ ассортимента кухонных смесителей

Рабочее дополнение к исходному проекту: загрузка очищенных данных в SQLite, аналитические SQL-запросы, разметка товарных групп и параметризованные выгрузки CSV.

**Готовые результаты:** [10 отчётов и проверка данных](../reports/sql/README.md). Запускать код для их просмотра не требуется.

## Быстрый запуск

Требуется Python 3.10+ с модулем `sqlite3` и SQLite 3.25+. Сторонние Python-пакеты и сервер базы данных для этого модуля не нужны. Основные ноутбуки проекта имеют свои зависимости.

Из корня репозитория:

```bash
python sql/assortment.py
```

Команда читает `data/processed/faucets_sales_cleaned.csv.zip` без предварительной распаковки, собирает базу `data/sql/faucets.sqlite`, проверяет перенос данных и сохраняет готовые отчёты в `reports/sql/`.

В репозитории также есть [готовая база в ZIP](../data/sql/faucets.sqlite.zip). Команды `reports`, `export` и `validate` автоматически восстанавливают её, если локального `.sqlite` ещё нет. При изменении CSV или справочника правил база пересобирается. Архив содержит только базу; он не заменяет исходный CSV.

### Примеры выгрузок

```bash
# Ассортимент брендов за 2024 год
python sql/assortment.py export --query brand_assortment --year 2024 --out reports/sql/brands_2024.csv

# Все сочетания бренд+наименование Shimizu за 2024 год
python sql/assortment.py export --query catalog_export --brand Shimizu --year 2024 --limit -1 --out reports/sql/shimizu_2024.csv

# Полная очередь проверки разметки
python sql/assortment.py export --query classification_review --limit -1 --out reports/sql/review_all.csv

# Все отчёты только за 2024 год в отдельной папке
python sql/assortment.py reports --year 2024 --output-dir reports/sql_2024

# Доступные запросы
python sql/assortment.py list

# Проверка целостности и сохранности исходных сумм
python sql/assortment.py validate
```

`--brand` задаёт точное нормализованное имя бренда. Параметры передаются в SQL отдельно от текста запроса. Если подходящих товаров нет, CSV содержит заголовок без строк. При фильтре по бренду доли в отчётах рассчитываются внутри выбранного среза.

Каталог, очередь проверки и повторяющиеся товаро-месяцы ограничены первыми 1000 строками; `--limit -1` снимает ограничение. Остальные отчёты выгружаются полностью.

## Данные и единицы анализа

SQL-модуль использует тот же очищенный набор, что и перепроверенные таблицы основного README: **218 668 строк, 31 исходное поле, январь 2023 — декабрь 2024**. Никакие новые продажи или цены не генерируются.

- Исходная строка — запись месячной статистики продаж. Это не отдельный заказ и не отдельный товар.
- `record_id` соответствует порядковому номеру записи в очищенном CSV без заголовка.
- `product_id` — технический ключ пары **нормализованный бренд + исходное наименование**. Таких пар **54 773**; уникальных наименований независимо от бренда **53 038**. Отдельного артикула в источнике нет, поэтому эти ключи не объявляются настоящими SKU.
- В одном месяце у одного такого ключа могут быть несколько исходных строк. **17 844** группы товар+месяц содержат повторы. Они сохраняются; автоматически удалять их как полные дубликаты нельзя.
- Ассортимент здесь означает товары в предоставленной статистике продаж. Данных об остатках и полном каталоге магазина нет.
- Выручка хранится целым числом рублей, количество — целым числом штук, как в данном CSV. Дробные суммы или количества загрузчик отклоняет вместо скрытого округления.

## Модель базы

| Объект | Содержание и ключ |
| --- | --- |
| `brands` | Справочник 1 179 брендов и групп; `brand_id` |
| `products` | Сочетания бренд+наименование; `product_id`, внешний ключ `brand_id` |
| `sales` | Все месячные наблюдения, продажи, цены и выбранные исходные признаки; `record_id`, внешний ключ `product_id` |
| `classification_rules` | Четыре правила соответствия `cat3_new` и `has_pullout` товарной группе |
| `metadata` | Контрольные суммы CSV и правил, версия схемы и исходные итоги |
| `v_sales` | Представление с `JOIN` справочников, `LEFT JOIN` правил и флагом необходимости проверки |

Схема: [schema.sql](schema.sql). Из 31 исходного поля перенесены поля, необходимые SQL-отчётам. Остальные доступны в неизменённом очищенном CSV. Историческая колонка `brand_abc` не копируется: ABC пересчитывается SQL-запросом для выбранного среза.

### Как интерпретировать расчёты

- Средняя цена продажи в SQL = `SUM(revenue) / SUM(quantity)`. Она взвешена количеством и отличается от невзвешенной средней цен строк исходного ноутбука. Колонка `price` и исторический `price_segment` сохранены из CSV.
- Ценовые сегменты не пересчитываются при выборе бренда или года: используются исторические квартильные границы проекта. Один технический ключ может встречаться в разных сегментах; количества ключей по сегментам не складываются в уникальный ассортимент.
- ABC пересчитывается для выбранного среза. Группы: накопленная доля `<=80%` — A, `<=95%` — B, остальные — C. Пересекающий границу бренд попадает в следующую группу, как в исходной версии проекта. При равной выручке порядок стабилизирован названием бренда.
- YoY сравнивает соседние годы, присутствующие в выбранном срезе. Для выгрузки только 2024 года предыдущий год отсутствует, поэтому рост пустой. Для сравнения 2024/2023 нужно выгрузить оба года без `--year`.
- `NoName/Прочие` — агрегированная исходная группа; она сохранена в рейтингах и долях и не интерпретируется как один производитель.

## Объяснимая разметка товарных групп

Правила находятся в [classification_rules.csv](classification_rules.csv), отдельно от Python-кода. Для текущего набора они покрывают четыре сочетания признаков:

| Правило | `cat3_new` | `has_pullout` | Группа |
| --- | --- | --- | --- |
| R01 | С фильтром | 1 | Отмечены фильтр и выдвижной излив |
| R02 | С фильтром | 0 | Отмечен только фильтр |
| R03 | Без фильтра | 1 | Отмечен только выдвижной излив |
| R04 | Без фильтра | 0 | Оба признака не отмечены |

Это учебные аналитические подкатегории внутри кухонных смесителей. SQL использует признаки, уже полученные в исходном Python-анализе, и не извлекает их заново из названий. Метка «Без фильтра» в источнике и значение `0` у текстового признака не гарантируют фактическое отсутствие функции. Поэтому новые группы описывают именно отметки в данных.

Каждая строка получает `rule_id`, подкатегорию и объяснение. Неизвестное сочетание признаков остаётся без правила и попадает на проверку. В каталоге несовпадающие характеристики одного технического ключа не заменяются произвольно одним из вариантов: выставляется `needs_review`.

На текущих данных все строки сопоставлены с правилами. Это **покрытие разметки**, а не доказательство точности исходного парсинга. Обнаружены пять строк с расхождением исходной `cat3` и дополненной `cat3_new`; всего в очереди проверки **685** технических ключей с расхождениями источников или разными характеристиками. Возможные причины включают дополнительное обогащение описаний и объединение разных товаров под одним названием. Автоматические исправления не выполняются.

## Проверка воспроизводимости

При построении базы проверяются: целостность SQLite, внешние ключи, сохранность числа строк, выручки, количества, годовых итогов и отсутствие потерь/размножения строк после `JOIN`. Подробный результат сохранён в [validation.json](../reports/sql/validation.json). Невалидная повторная загрузка не заменяет предыдущую рабочую базу.

```bash
python -m unittest discover -s sql/tests -v
```

Девять тестов покрывают сохранение повторяющихся наблюдений, разделение одинаковых названий по брендам, неоднозначную разметку, очередь проверки, фильтры, средневзвешенную цену, отсутствие предыдущего года, передачу параметров, ZIP-ввод, восстановление готовой базы и пустые выгрузки.
